# Codex Rules Hygiene

## Overview

Keep `default.rules` as a compact policy layer rather than an approval log.
Always choose an explicit mode before inspecting or changing host state.

## Choose A Mode

### Audit Mode

- Use for inspect, audit, report, or recommendation requests.
- Choose a light audit for one known recent growth burst; choose a full audit for whole-file, stale-gap, periodic, or cold-start requests.
- Keep the run read-only: leave `default.rules`, baselines, safety snapshots, and journals unchanged.
- Resolve the best existing comparison anchor, classify the delta, and report an exact proposed change.
- If no clean baseline or older backup exists, inspect the current file as a cold-start inventory and report the bootstrap apply plan while leaving host state unchanged.
- An audit-only request never becomes writable merely because it found drift.

### Apply Mode

- Use when the user requested cleanup/apply, or when a prior audit proved an exact change and the active task already authorizes applying it.
- Carry forward independent SHA-256 digests for the audited live-rules bytes and the exact candidate bytes. Stop if either digest or either byte sequence is missing.
- If there is no approved content change, report a no-op and create nothing.
- Otherwise use the skill-relative transaction helper below; do not rewrite live rules directly.

## Audit Workflow

1. Resolve the comparison anchor without writing.
- Prefer `~/.codex/rules/default.rules.clean-baseline`.
- Otherwise use the most recent older `default.rules.bak-*`.
- If neither exists, mark the audit as a cold start and inspect the current file directly.

2. Diff first, then classify each added rule.
- `stable prefix`: a categorical command family likely to recur with the same argv prefix.
- `wrapper drift`: shell, `env`, prompt-file, or fixed-temp plumbing obscures an existing stable owner.
- `helper gap`: a repeated workflow lacks a safe helper interface.
- `approval log`: a one-off URL, PR, SHA, prompt, temp path, or scenario literal.

3. Propose the narrowest owner.
- Keep a stable prefix only when it is intentionally reusable.
- Fix wrapper drift in the invocation or helper instead of preserving the wrapper literal.
- Route repo-specific helper gaps to repo-local owners and host-level cross-repo gaps to personal skills.
- Use [$codex-skill-authoring](../codex-skill-authoring/SKILL.md) when the instruction layer or owner is unclear.
- Use [$codex-session-mining](../codex-session-mining/SKILL.md) only for a targeted origin backtrace when the diff is ambiguous.

4. Bind any proposed apply plan without writing host state.
- Record separate SHA-256 digests for the exact audited `default.rules` bytes and the exact candidate bytes.
- Produce the exact candidate bytes or a deterministic patch that recreates them.
- Name the comparison anchor and validator that apply mode must revalidate.
- Keep the audit read-only: do not create the candidate file, backup, lock, receipt, baseline, or journal update.

## Apply Transaction

1. Identify the existing rules-policy validator. If no trustworthy validation gate can be named and run, stop before creating a backup or touching live rules.
2. Require one writer protocol for the transaction. Every legitimate rules writer must use the helper's shared lock, or the caller must first prove other writers quiescent; POSIX advisory locks cannot protect against a writer that ignores them.
3. Write the reviewed bytes only to a task-scoped candidate source, then invoke `scripts/apply_rules_transaction.py apply` with the audited live SHA-256 digest, the independent audited candidate SHA-256 digest, a fresh timestamped backup basename, an owner-private recovery receipt path, and direct validator argv containing one `'{rules}'` placeholder. The helper derives live `rules/default.rules` and its persistent lock from `CODEX_HOME` (falling back to the default Codex home). Before candidate admission or lock creation, it rejects the receipt and every derived terminal/result/prepared/lock path whose lexical or canonical namespace is the fixed stage leaf, an ancestor or descendant, a symlink/canonical-identity alias, or a case-folded/Unicode-normalized alias under the same descriptor-bound rules parent. It also pairwise rejects rules, backup, lock, receipt, terminal, result, and prepared leaves that share a descriptor-bound parent and collide after NFKC normalization plus case folding.
4. Let the helper bind and digest-check the candidate source before copying it. Every untrusted pathname used to bind a required regular file is opened nonblocking and no-follow, then immediately rejected by descriptor type before any read; a FIFO replacement therefore cannot stall either pre-lock admission or a lock-held apply/recovery path. An apparent no-change takes the shared lock, binds that exact lock object and rules parent, admits live metadata and link policy, revalidates the source binding, verifies that any already-existing fixed stage is the bound metadata-admitted empty root, and returns `no_change_after_lock` without creating a stage or starting a validator. For a real change, the first validator receives only an unlinked descriptor-backed copy outside the rules directory; the helper passes that FD directly to the synchronous child, revalidates every protected property and admitted metadata on the held FD, then revalidates the original source. A validator broker, daemon, container, or grandchild that closes inherited FDs cannot consume this first-pass path. After both checks pass and while holding the lock, the helper preflights the fixed stage and its metadata before creating any prepared candidate, terminal reservation, receipt, or backup. Only a clean preflight may create the exact owner-private prepared candidate at the receipt-sibling recovery locator; candidate bytes do not enter the fixed stage until the schema-v4 receipt is durable. Its validator supervisor requires a finite deadline, a standalone single-threaded main process with default `SIGCHLD` disposition, enforces an aggregate output-byte ceiling, and independently enumerates live same-process-group members before accepting completion. Before `Popen`, it masks and installs a first-signal gate for `SIGINT`, `SIGTERM`, and `SIGHUP`; it arms only after the child PID/PGID is parent-bound, performs every group inventory and TERM/KILL operation while the unreaped leader still pins that numeric PGID, and makes the final direct-child wait the last process-group lifecycle operation. Setup, observation, cancellation, process-inventory, and other supervisor failures use the same emergency cleanup. A raw wait/pipe error or forwarded signal remains the primary failure while TERM/KILL, drain/reap, observer, selector, both pipe closes, and signal restoration all run best-effort and attach structured secondary evidence. If a managed signal interrupts the second, live-path validator after replacement, the helper first runs the same rollback/recovery state machine, then returns `128 + signal` with `interrupted` as the primary outcome plus receipt, backup, recovery locators, and the nested rollback/recovery result; cleanup and finalizer failures remain secondary evidence. A cleanup-only failure is `validator_cleanup_failed`; restored signal-handler identities and the inherited mask are reread before success. The helper revalidates identity, content, access policy, and link policy on the held candidate and live descriptors, plus file flags, xattrs, and ACL admission, immediately before exchange and after installation.
5. The fixed owner-private staging directory `.default.rules.transaction-stage` is reusable infrastructure: a normal transaction requires the currently named object to be owner-only, metadata-admitted, empty, and descriptor/path identity-bound. `mkdir` does not return a creation FD, so the helper never treats a later stat/open as proof that the transaction still owns the object created by `mkdir`, and it never chmods or removes the named stage. A stage whose owner permissions were masked by the caller's umask, or whose name was replaced before binding, is retained and fails closed unless the current object independently satisfies the complete stage policy. After the artifact-free preflight, the helper creates and fsyncs the exact prepared candidate and immutable recovery-terminal reservation, writes and fsyncs the schema-v4 receipt that binds both recovery locators and the prepared object's identity, and only then creates or opens and independently admits the fixed stage before atomically moving that same candidate object into `transaction-stage/candidate`. The persistent lock has a different creation contract: its `O_CREAT|O_EXCL` FD is authoritative creation identity, so the helper proves FD/path identity, current owner, regular type, and one link before descriptor-only `fchmod(0600)`, then proves all properties again. The receipt and rules parents must be on one filesystem, and the receipt parent cannot overlap the fixed stage namespace. Immediately before it exchanges the private candidate with live rules, the helper revalidates all bound evidence and re-proves that the backup leaf—including a case-insensitive filesystem alias—is still absent. The exact displaced original inode later occupies the staged candidate leaf and is published directly to the absent formal backup with atomic no-replace rename; every affected directory is fsynced. A successful apply, automatic rollback, or recovery leaves the fixed stage empty without unlinking, removing, quarantining, or reusing any exposed child inode. Apply performs final evidence validation and fixed-stage cleanup while the shared lock is held, but keeps the receipt, terminal, optional terminal result, and both parent descriptors open until the lock context has completed its final lock revalidation and attempted the lock-FD close. Body, before-release, or final-revalidation failures remain primary; a lock-close fault is structured release-uncertainty and becomes primary only when no earlier failure exists. Every remaining bind, read, rollback, stage, and evidence descriptor cleanup is best-effort-all in deterministic order, attaching every EIO/EINTR or other close failure to the existing property/tamper/rollback/terminal outcome instead of replacing it or skipping later descriptors. Private-stage close failures additionally enter the persistent result accumulator with stable `cleanup_reason` and `descriptor_class`; an otherwise clean apply becomes nonzero `recovery_required` while retaining `operation_status: applied`, and a pre-existing failure keeps its primary status. Final persistent-evidence or rules-parent descriptor uncertainty similarly converts an apparent `applied` or either `no_change_after_lock` path into nonzero `recovery_required` with `final_evidence_descriptor_close_failed`; it can never authorize a baseline refresh. Any unexpected remaining entry or replaced stage root is retained and blocks success or a later apply. Treat only `applied` or `no_change_after_lock` with no cleanup uncertainty as success. The helper re-runs the validator against live rules; a post-exchange failure rolls back by exchanging the bound backup and live objects only while live still matches the exact installed protected properties. If an atomic outcome cannot be proved, it returns `recovery_required` and copies every still-bound source/destination FD into fsynced recovery files. Count an object as retained recovery evidence only after the locator is bound and the held origin and recovery-copy descriptors, complete protected properties, metadata admission, and directory entries are revalidated; `retention_incomplete` explicitly means descriptor cleanup may destroy an unlinked object.
6. Use `scripts/apply_rules_transaction.py recover --receipt <path>` only for that receipt. Schema-v4 adds the durable prepared state `Q=(original live, backup missing, stage missing, installed prepared sibling)` to schema-v3's `P`, `X`, `C`, and `R` identity states. Recovering `Q` records the verified original terminal state without deleting or moving the prepared object; repeated recovery is idempotent. `P→X→C→R` uses the same exchange/no-replace operations. Under the lock, recovery records exact live/backup roles—and, when needed to prove untouched v4 `Q`, a bounded stage/prepared probe—before strict terminal reservation/result binding or validation can fail. A reserved terminal clears deferred prior-mutation evidence only after the complete four-role observation proves exact `Q`; every other reserved-terminal or state-none observation promotes that evidence when mutation cannot be excluded. Thus a lost `P` candidate, a lost `R` backup, or another reserved-role tuple compatible with prior mutation is `recovery_required` with mutation journal and locators rather than a pre-mutation refusal. Installed live plus the exact original in the staged leaf also proves a prior exchange even when backup or prepared state is unknown. A terminal failure after proved or possible v3 `P`, v4 `P`, `X/C/R`, or apply mutation is `recovery_required` with mutation journal and locators; only exact pre-mutation `Q` may refuse that terminal drift. Schema-v4 always compares reservation identity, size/digest, access policy, and link policy exactly with the receipt snapshot; only schema-v3 explicitly permits the historical same-inode restored rewrite. After terminal validation, a reserved terminal plus primary and auxiliary evidence that proves untouched `Q` may still refuse later prepared drift as pre-mutation; a published Q result, observed `P/X/C/R`, or auxiliary state ambiguous with a prior mutation makes later drift `recovery_required`, including on retry. The receipt file and owner-private receipt-parent descriptors stay open from secure parse through lock acquisition, every mutation, terminal publication, final validation, and lock release; exact pathname entry, identity, bytes, access policy, single-link policy, and parent identity/policy are revalidated at every boundary. Only provably pre-mutation drift is `recovery_refused`; once any delegated v3/v4 mutation may have started, later binding failure remains `recovery_required` and includes its observed mutation journal, state, and recovery locators. Legacy rollback now records mutation entry immediately before its exchange attempt and completion after a proved exchange, so later receipt-parent or lock finalization failure also retains the journal and locators. Terminal publication never truncates the reservation: it fsyncs a fresh owner-private, retry-stable pending result, revalidates descriptor, entry, exact bytes, owner-only policy, one-link policy, and both fsyncs after every pre-rename failure, and reports an exact `pending_locator` only after `observation_matches` succeeds and the bound parent plus descriptor/entry/content/policy are revalidated again. Otherwise it reports `retention_incomplete`. A retry scans the bounded pending namespace before creating anything: it adopts the sole exact result or blocks on incomplete/ambiguous evidence, so unknown pending files cannot accumulate without bound. It then atomically publishes the sibling `.result` entry without replacement, fsyncs the directory, and keeps both descriptors bound through lock release. Result, reservation, receipt, and every held parent close best-effort-all; cleanup failures are structured and appended to `recovered`, `recovery_required`, or `recovery_refused` rather than changing the primary result to `runtime_error`. Private-stage close failures follow the same schema-v1/v2/v3/v4 accumulator rule; a would-be `recovered` or `already_original` success becomes nonzero `recovery_required` with its original `operation_status`. Schema-v3 compatibility retains its four-state recovery. Legacy schema-v1/v2 receipts retain copy-backup recovery semantics but now bind their exact receipt/rules parents under the lock, and retained fixed-stage evidence or refused cleanup returns `recovery_required` rather than success. Schema-v1 receipt snapshots always normalize historical link count to unknown; an explicitly supplied `object_policy.nlink` is accepted only when it is exactly `1` and never becomes current policy. Every current live, backup, stage/recovery source, reservation, result, and restored-terminal observation must independently prove `st_nlink == 1` at each binding and revalidation. `already_original` requires either the receipt's exact original identity or a verified recovery-terminal result created for that transaction; matching bytes and policy on a different unrecorded inode are refused.
7. After a successful full cleanup with no intentionally retained drift debt, refresh `default.rules.clean-baseline` from the verified live file. Never refresh it after audit mode, a light cleanup, a rollback, `recovery_required`, or a failed/partial apply.
8. Write only the necessary adopted-journal or focused-note update when apply adopts a durable rule/helper/skill decision or records the successful full-cleanup baseline. Use an owning repo's existing journal when already adopted; otherwise use a nearby focused note instead of bootstrapping a tracker. Do not journal a read-only audit or no-op apply.

Cleanup, lock-finalization, and pending-result retention failures remain structured evidence on Python 3.9 and 3.10. Python 3.11+ exception notes are best-effort diagnostics only; missing or faulty `add_note` support never replaces the primary transaction outcome.

## Ownership And Guardrails

- Rules govern reusable approval families; skills decide when to use them; helpers encode repeated fragile mechanics.
- Load [references/audit-cadence.md](references/audit-cadence.md) before apply mode for the helper command, output states, and recovery boundary.
- Use `host_executable()` only to harden a small trusted basename family, not to excuse wrapper drift.
- Do not widen rules because one literal was inconvenient.
- Do not keep fixed issue IDs, PR numbers, prompt files, review bundles, or task-scoped temp paths after their stable owner is known.
- Read [references/audit-cadence.md](references/audit-cadence.md) for light/full audit cadence and classification examples.
